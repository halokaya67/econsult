Flow record · 001-econsult-flow

What the AI workflow did

The e-consult submission flow was built by AI inside a gated loop, and every gate left a file behind. This page walks the loop in the order it ran and links the evidence for each stage. Everything is local: no network, no server, and every link on this page is relative.

The loop, in order

  1. Brief → research
  2. Spec, five checker rounds
  3. Plan, three rounds, 22 steps
  4. Implementation review
  5. UI verification, four lanes
  6. Reviews after implementation
  7. Hand-in documents
  8. What the loop caught

Every number on this page was counted from the files in this repository, and each section says which file it was counted from. Commit hashes are the ones on the feat/econsult-flow branch as it stands, so git show <hash> works from a clone; the execution log at the end of plan.md records the hashes as the run itself saw them, before the branch was rebased.

01Brief → research

Before anything was specified, nine platform topics were researched by agents that had to open their sources and mark unopened recall as unverified; a second pass then tried to refute every claim against the installed SDK, and a completeness critic sent six remaining gaps back for one more round.

02The spec, and its five checker rounds

The spec was written from the brief and the research, then read by a separate checker five times. No round found a blocker; each one traded a plausible claim for a verified one, and the last round left two information items and no warnings. PASS_WITH_FLAGS is the flow's proceed verdict — only a FAIL blocks a gate — so none of these rounds held the spec up: the flags were tracked, and each round's findings were fixed in the next revision, which the following round re-read and recorded as RESOLVED.

03The plan, its three rounds, and the twenty-two steps

The plan broke the spec into twenty-two test-first steps, each with the files it was allowed to touch and the commands that would verify it. It failed its checker three times running. A FAIL blocks: no failed revision could reach the plan gate, so each round's blockers were removed in the next revision and re-read by the round after it. What the implementation was executed from is revision 3.1, which the user approved at the gate.

The Accessibility Inspector audit

Xcode's Accessibility Inspector was run against the app on the iPhone 17 simulator with the default audit options. Five states were audited — home, step 1 loaded, step 3 with the empty-message error, the developer-settings modal, and the partial-failure confirmation — and each returned 0 warnings, 0 duplicates. Because a row of zeros only means something if the engine was looking, the same audit was pointed at Expo Go's own developer menu as a positive control, in the same process: 22 warnings.

Read verbatim from the Inspector's results outline, transcribed in phone/s10r-audit-results.md; the screenshots pairing each state with the Inspector window are the s10r- series on phone.html.

08What the loop caught

Six cases the README's control-point table cites, each one a defect that the stage before it had passed. They are the argument for the gates.

  1. The upload recommendation would have failed on the first byte

    The research first recommended React Native's classic form-data file part. The adversarial pass read the installed Expo source and found that Expo's own fetch, which is the global on SDK 57, rejects that value outright. No unit test would have caught it without a real server.

    Evidence: research.html, follow-up 1 and the image-picker topic's verdict.

  2. The plan would have stopped the app from starting

    It placed the screen tests next to the screens, under src/app — where expo-router loads every file as a route. The plan checker found it on paper, before any code existed; the failure mode is app start-up, not a red test.

    Evidence: plan review 1, one of that round's six blockers.

  3. Five of the six screen steps passed their tests and failed on the simulator

    A header label clipped at the largest text size (T016); scroll-to-error doing nothing under the New Architecture, and then an error still rendered off screen once it worked (T017, three re-checks); the message field scrolling its own label out of view (T018); a failed photo retry changing nothing on screen (T019); the offline switch pushed past the screen edge (T020). Each was found by driving the simulator after the step's tests were green, and each was fixed before the step was committed. Jest renders no layout and no text scaling.

    Evidence: the re-check pages for T016, T017, T018, T019 and T020, collected on visuals/index.html.

  4. A corrected question kept announcing its old error

    On Android, a content description set back to undefined is never cleared, so an answered choice question still carried “Error: This question is required” in its accessible name. Invisible to a sighted user and to every test; only TalkBack showed it.

    Evidence: defect 1 on the Android lane, with its re-check.

  5. A photo pick blanked the screen on a real iPad

    Attach a photo, scroll down for Send, and the message step went blank — on physical hardware, in a state both simulators had rendered correctly. The later iPad pass confirms it no longer reproduces, with Send hittable at both text sizes.

    Evidence: “The blank message step is fixed” in device.html.

  6. The same error was spoken twice

    A required-question error was announced and then spoken again as the focused field's name, and “Message sent” was spoken as a status and as a heading. Both are correct on screen and wrong in the ear; a validation error is now spoken by the focus move alone, and the confirmation heading speaks itself once.

    Evidence: defects A and B under TalkBack spoken text, and their re-check.

Reading notes

  • Every link on this page is relative and every file it points at is in the repository. The pages style themselves with system fonts and the two diagrams on how it works are pre-rendered SVG, so opening the record from the file system works with no network; npm run showcase does exactly that. The only outward links are the sources the research and review pages cite, and no page needs them to render.
  • Pages ending in .html are rendered copies of the markdown the flow wrote at the time — the wording, the evidence lines and the verdicts are unedited. The .md links go to those sources.
  • Screenshots are downscaled copies, long edge at most 900 px, so the record stays small enough to live in the repository. The accessibility-tree and speech dumps are the originals.
  • The lanes on the two physical devices are the most recent work, and they leave three defects unfixed. They are described where they were found, not hidden: one on the Samsung tablet, recorded as a known limit, and two on the iPad that stand as observations — a layout condition that could not be reproduced, and a UIKit affordance a React Native view does not inherit.
