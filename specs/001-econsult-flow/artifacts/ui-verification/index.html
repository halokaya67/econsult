What was checked, and how it came out

Both lanes were driven with the same tooling (agent-device 0.21.0) at the medium text size unless a scenario says otherwise, and each lane's result comes from the accessibility tree and the screenshots rather than from an eyeball impression. The one exception is the Accessibility Inspector audit, which was driven through AppleScript UI scripting because the Inspector is not an app the device driver can reach. Neither lane produced a crash, a red box or a Metro warning beyond the empty-cache notice.

The one defect, found and fixed

Scenario 7 on the phone. With a draft in progress, pressing Home raised the “Discard your message?” dialog as designed, and “Keep writing” kept the draft. But “Discard” only dismissed the dialog: the app stayed on step 1, the draft survived, and the dialog re-raised on every further Home press — so a patient who chose to discard was trapped in the flow. It failed silently, with nothing in the log.

The fix was made and the scenario re-driven on the new head. “Discard” now lands on Home, the next “Write to your practice” starts with an unselected step 1 and an empty message field, and the back-action variant of the same path behaves identically. Both runs are on the phone lane page: the first-run screenshots are the s07- series, the re-drive is s07r-.

The accessibility audit, completed on a re-run

Scenario 10 is an Xcode Accessibility Inspector audit of the app's screens. On the first run it could not be done: the Inspector launched, but every click inside it was refused, because its window belongs to an XPC helper process that the automation's allowlist cannot grant. Nothing was audited and the scenario was reported INCONCLUSIVE rather than quietly dropped.

It was then re-run through AppleScript UI scripting, which could drive Run Audit and read the results outline. One step stayed manual: the target picker would not bind the simulator from a script — a scripted selection changed the toolbar label but left every audit returning an empty table — so the user selected “Simulator › Expo Go” by hand once, after which the picker read the app's own process id.

Five states were audited and each returned 0 warnings, 0 duplicates: home, step 1 loaded, step 3 with the empty-message error, the developer settings modal, and the partial-failure confirmation. Because a run of zeros only means something if the engine was actually looking, the same audit was pointed at Expo Go's own developer menu as a positive control, in the same process and binding: it returned 22 warnings across clipped text, contrast, Dynamic Type and element description. The engine was live and running those categories, so the five clean results are real.

The one manual step affects how reproducible the harness is, not what the audit found. Both runs are on the phone lane page — the first run's log, then the s10r- screenshots pairing each app state with the Inspector window that audited it, plus the results table and the Inspector tree dump.

One layout observation on the tablet

Not a failure. The form column runs 802 pt wide in an 834 pt portrait canvas (1178 pt of 1210 pt in landscape), so body copy and the full-width buttons stretch nearly edge to edge. A centred column of roughly 560 to 680 pt would read better on iPad and would not change phone rendering.
