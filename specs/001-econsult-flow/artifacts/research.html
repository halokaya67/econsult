Topic: image-picker

Photo capture and library selection with expo-image-picker on Expo SDK 57 (Expo Go, iOS simulator / Android emulator, fetch+FormData upload)

Recommendation

Add expo-image-picker with npx expo install expo-image-picker (resolves to 57.0.x) — it is Expo Go compatible on SDK 57, so nothing about the photo step forces a custom development build; that is the single biggest reason to pick it over expo-camera-based custom UI for this case study. Add the config plugin entry to app.json next to expo-router/expo-splash-screen with Dutch usage strings (e.g. cameraPermission: "Sta toe dat de app de camera gebruikt om een foto bij uw e-consult te voegen", photosPermission: "Sta toe dat de app uw foto's gebruikt om een foto bij uw e-consult te voegen", microphonePermission: false since you never record video) — the plugin only takes effect for prebuild/EAS builds, but including it documents intent and keeps the project buildable. In code, use the hooks (const [cameraPermission, requestCameraPermission] = useCameraPermissions()) so permission state is reactive and you can render a distinct "permission denied → open Settings" state rather than a silent no-op, which matters for elderly users. Call launchImageLibraryAsync({ mediaTypes: ['images'], allowsEditing: false, quality: 0.6 }) and launchCameraAsync({ mediaTypes: ['images'], quality: 0.6 }); pass mediaTypes as a string array (not the deprecated MediaTypeOptions enum) and always set quality explicitly, because the default 1.0 produces multi-MB JPEGs that are hostile on poor connections. Guard results with if (result.canceled) return; then take result.assets[0] and keep { uri, width, height, fileName, fileSize, mimeType } in state for the preview (render with expo-image, already a dependency, and give the preview an accessibilityLabel plus a clearly labelled "Foto verwijderen" button rather than an icon-only X). For the two-call send, POST the e-consult JSON first, then upload with const body = new FormData(); body.append('photo', { uri: asset.uri, name: asset.fileName ?? 'foto.jpg', type: asset.mimeType ?? 'image/jpeg' } as any); await fetch(url, { method: 'POST', body }) — do not set Content-Type yourself, let RN generate the multipart boundary, and note the as any cast is needed because RN's DOM-typed FormData signature does not describe the {uri,name,type} part. Handle the platform asymmetry explicitly: on the iOS simulator the camera button cannot work, so detect and show a friendly "camera niet beschikbaar in de simulator" hint and demo the flow from the photo library, while the Android emulator's virtual scene camera (with an imported JPEG of, say, a rash or a wound) lets you record the real capture path for your demo video. Finally, wire getPendingResultAsync() on Android mount so a low-memory MainActivity kill during capture does not silently drop the patient's photo, and treat the attachment upload as independently retryable — the e-consult itself is already created after call one, so the offline/error state should say "bericht verstuurd, foto nog niet" rather than implying total failure.

Topic: network-offline

Offline detection and slow/failing request handling for the e-consult send flow in Expo SDK 57 (Expo Go compatible)

Recommendation

Use expo-network (npx expo install expo-network) and nothing else. Both candidates run in Expo Go, so the deciding factors are payload and privacy: expo-network is a first-party Expo module already aligned to SDK 57, adds its own Android permissions, needs no config plugin, and — critically for a GP portal — never phones a third party, whereas NetInfo's isInternetReachable repeatedly HTTP-probes https://clients3.google.com/generate_204 by default, which you would have to repoint at a practice-owned endpoint before it is defensible under GDPR. NetInfo's only real advantage (an actual internet probe rather than link state) is one you should not depend on anyway.

Shape it as a two-layer design, because the SDK-57 platform split makes a network flag an advisory hint, not a truth:

Layer 1 — the banner (advisory). Wrap useNetworkState() in a useIsOffline() hook that returns offline only when isConnected === false || isInternetReachable === false, and treats undefined/unknown as online. Fail-open matters here: an elderly user on a flaky 3G connection must never be locked out of sending by a state the module could not determine. Render a persistent banner above the form — large type that respects Dynamic Type, an icon plus Dutch text (not colour alone), accessibilityRole="alert" with accessibilityLiveRegion="polite" on Android, and an AccessibilityInfo.announceForAccessibility call on the offline→online and online→offline transitions so VoiceOver/TalkBack users hear the change without hunting for it. Note the iOS caveat explicitly in your write-up: since isInternetReachable mirrors isConnected on iOS, a captive-portal or dead-router Wi-Fi will read as online there while Android would correctly report unreachable.

Layer 2 — the send path (authoritative). Keep the send button mounted and focusable but disabled when offline, with accessibilityState={{ disabled: true }} and an accessibilityHint that says why and what to do ("Geen internetverbinding — uw bericht wordt bewaard op dit scherm"); removing the button strands screen-reader users with no explanation. Because the flag can be wrong, the request itself is the real check: wrap both calls in a small fetchWithTimeout(url, init, ms) that creates an AbortController, arms setTimeout(() => controller.abort(), ms) (no AbortSignal.timeout available on this RN version), and clears it in finally. Use roughly 15s for the create call and 30–45s for the attachment upload. In the catch, branch on err.name === 'AbortError' (timed out — "Het duurt te lang, probeer het opnieuw") versus a TypeError from fetch (connection failed) versus a non-2xx status, and drive a single sendState machine: idle | sending | error | sent.

Retries, with no queueing. Manual retry as the primary affordance: a large "Probeer opnieuw" button in the error state that re-runs only the step that failed. Add automatic retry sparingly and only where it is safe — at most two attempts with ~1s then ~3s backoff plus jitter. The create call is not idempotent, so either send an Idempotency-Key header (a UUID generated once per composed e-consult and reused across retries) or do not auto-retry it at all; say which you chose in the README. The attachment upload is keyed to the returned e-consult id and is therefore safe to auto-retry. Handle the partial-failure case deliberately, since it is the most interesting thing about a two-call flow: if create succeeds and upload fails, go to the confirmation screen with the e-consult marked sent and a separate inline "foto niet verzonden — opnieuw proberen" affordance. Never re-post the e-consult to recover a failed photo.

Testing story for the README. iOS simulator: it uses the Mac's network stack, so switching the Mac's Wi-Fi off is the fastest offline test, and Network Link Conditioner (Additional Tools for Xcode) gives the slow/lossy profiles for timeout and spinner behaviour. Android emulator: adb emu gsm data off / adb emu gsm data home for offline, and adb emu network delay gprs + adb emu network speed edge to exercise the sending state and the 15s abort.

Cost callout for the case study: zero. expo-network is bundled in Expo Go, so a clean clone plus npx expo install expo-network and npx expo start works on both simulators with no prebuild, no EAS build, and no native config.

Recommendation

KEEP (hard requirements — removing any breaks the app): expo, expo-router, expo-constants, expo-linking, react-native-safe-area-context, react-native-screens, react, react-native, typescript, @types/react. Topic: keyboard-safe-area

Keyboard avoidance and safe areas for the e-consult flow in Expo SDK 57 / RN 0.86 (Expo Go only)

Recommendation

Ship the core-RN layout as the default and treat keyboard-controller as an optional upgrade.

Baseline (zero new dependencies, guaranteed to run from npx expo start in Expo Go):

  1. Leave app.json alone — do NOT add softwareKeyboardLayoutMode. The default "resize" makes the Android window shrink for the keyboard, which is exactly what you want with a single ScrollView and no bottom tab bar; "pan" would break scrolling to the button.
  2. One ScrollView per step, and put the primary action ("Volgende" / "Versturen") as the LAST CHILD INSIDE the scroll content, not in a pinned footer. This is the single change that removes the whole class of KeyboardAvoidingView bugs: RN's KAV measures its own onLayout frame and applies paddingBottom/height to itself, so a pinned footer + ScrollView + expo-router header needs a hand-tuned keyboardVerticalOffset and still lags on Android (Android listens to keyboardDidShow, not WillShow). A button inside the content also survives 200%+ Dynamic Type, which a fixed-height footer does not — relevant for elderly GP patients.
  3. ScrollView props: keyboardShouldPersistTaps="handled" (otherwise the first tap on the button only dismisses the keyboard — a real two-tap bug for elderly users), automaticallyAdjustKeyboardInsets (iOS-only, default false; handles the keyboard inset on iOS with no KAV at all), keyboardDismissMode={Platform.OS === 'ios' ? 'interactive' : 'on-drag'}, and contentContainerStyle={{ flexGrow: 1, padding: 16, paddingBottom: 24 + insets.bottom }}.
  4. Safe areas: expo-router already mounts SafeAreaProvider, and the Stack header already consumes the top inset — do not add a SafeAreaView with top under a header or you pay the inset twice. Use useSafeAreaInsets() and apply only bottom (plus left/right) as padding on the scroll content, since Android edge-to-edge is always on from SDK 54+ and content draws under the system bars. Do not mix SafeAreaView and useSafeAreaInsets on the same screen (documented flicker).
  5. Only if the design demands a truly pinned footer: wrap the FOOTER (not the ScrollView) in <KeyboardAvoidingView behavior={Platform.OS === 'ios' ? 'padding' : undefined} keyboardVerticalOffset={headerHeight}>. Passing undefined on Android is Expo's own recommendation and avoids double-counting adjustResize.

Optional upgrade, still Expo Go-safe: npx expo install react-native-keyboard-controller (pins 1.21.9 for SDK 57), wrap the root _layout.tsx in <KeyboardProvider>, then use KeyboardAwareScrollView for the question/message steps and KeyboardStickyView for a footer button that tracks the keyboard frame-by-frame. Expo's SDK 57 reference page marks this library inExpoGo: true, so it needs no development build — but Expo's own keyboard-handling guide still carries a stale "not included in Expo Go" line, so verify on a real Expo Go SDK 57 client before you depend on it in a submission that must run from a clean clone, and call the discrepancy out in the README. Note it also requires reanimated (already present at 4.5.1).

For the sending/offline/error states: keep the same ScrollView shell and swap only the content, so the keyboard/inset behaviour is defined in one layout component (e.g. FormScreenScaffold) rather than repeated per screen.

Packages involved: expo, expo-router, react-native, react-native-safe-area-context, react-native-keyboard-controller, react-native-reanimated, react-native-screens

Topic: accessibility

Accessibility APIs in React Native 0.86.3 / Expo SDK 57 for a VoiceOver- and TalkBack-usable e-consult form flow (labels, error announcement, focus management, touch targets, font scaling, testing)

Recommendation

NOT VERIFIED THIS RUN (mark down accordingly): VoiceOver does not run on the iOS Simulator — you must use Xcode's Accessibility Inspector against the Simulator, and test real VoiceOver speech on a physical device. Apple's doc pages (developer.apple.com HIG/documentation) are JS-rendered and returned title-only through WebFetch on every attempt; the claim came from developer.apple.com search snippets of Apple's archived "Testing Accessibility of iOS Apps" technote, not a page body I opened. Treat as strong-but-unconfirmed and verify before putting it in the write-up.

CONCRETE PLAN FOR THE E-CONSULT FORM

  1. Error → input association. There is no aria-describedby/aria-errormessage in RN 0.86.3 (fact 1), and aria-live is Android-only (fact 2). So do all three layers: (a) Put the error text INTO the input's own accessible name: accessibilityLabel={hasError ? \${label}. Fout: ${errorText}` : label}— this is the only mechanism that works identically on VoiceOver and TalkBack. (b) Render the visible error node withaccessibilityLiveRegion="polite"(Android picks it up automatically; no-op on iOS). (c) On iOS, callAccessibilityInfo.announceForAccessibility(errorText)when the error first appears. Gate it behindawait AccessibilityInfo.isScreenReaderEnabled()` and debounce — announcements fire on every render otherwise. Do NOT rely on accessibilityLabelledBy/nativeID: it is Android-only (fact 5).

  2. Focus management between steps (recipient → questions → message → photo → sending → confirmation). On validation failure, move screen-reader focus to the first invalid field using the non-deprecated call: AccessibilityInfo.sendAccessibilityEvent(inputRef.current, 'focus') — pass the ref directly, no findNodeHandle (fact 4). For a TextInput you usually want both: inputRef.current?.focus() to raise the keyboard AND sendAccessibilityEvent to move the a11y cursor; they are independent. On route change under expo-router, announce the new step ("Stap 2 van 4: vragen") via announceForAccessibility after a short delay, since neither platform reliably announces RN screen transitions.

  3. Grouping. Wrap each question (label + helper + control) in a <View accessible accessibilityRole="radiogroup"> only when you want ONE swipe stop; note that accessible on a parent collapses all children into a single element and children become unreachable — for a text question you almost never want this, because the TextInput must stay individually focusable. Use grouping for the recipient cards (one stop per recipient: name + role + hint) and leave form fields ungrouped.

  4. Choice questions. Use Pressable with accessibilityRole="radio" inside a parent accessibilityRole="radiogroup", and accessibilityState={{ checked: selected }}. Pressable already gives you accessible=true and maps disabled into accessibilityState (fact 7), so do not duplicate it. Add accessibilityHint sparingly — on Android TalkBack hints cannot be turned off by the user, so a hint on every option becomes verbose noise for elderly users.

  5. Touch targets + hitSlop. Target 48x48 as the single number (satisfies Android's 48dp and exceeds Apple's 44pt, fact 12). Prefer real minHeight/minWidth over hitSlop for the primary actions (Verstuur, Kies ontvanger, Verwijder foto) — hitSlop enlarges the press region but I could NOT confirm this run that it enlarges the VoiceOver/TalkBack activation frame, so a hitSlop-only target may be big for fingers and small for a screen reader. Use hitSlop only as a secondary cushion on small icon buttons like the photo "remove" X.

  6. Font scaling for large text. Leave allowFontScaling at its default true (fact 9) — do not disable it anywhere; elderly Dutch patients are the whole point. Apply maxFontSizeMultiplier only on genuinely constrained chrome (a fixed-height header), around 1.5-2.0, and never on body copy, question text, or the message field. Read scale from useWindowDimensions().fontScale, NOT PixelRatio.getFontScale() — the latter returns the device pixel ratio (typically 3) when no font scale is set (fact 10), which will silently break any if (fontScale > 1.5) branch. Use fontScale to switch button rows from horizontal to vertical stacking at large scales rather than to shrink text.

  7. State announcements for sending/offline. Give the send button accessibilityState={{ busy: isSending, disabled: !canSend }} and change its accessibilityLabel across the two calls ("Bezig met versturen", "Bericht verstuurd, bijlage wordt geüpload"). For the offline banner use accessibilityLiveRegion="polite" plus a one-shot announceForAccessibility on the offline→online transition. Give the confirmation screen's heading accessibilityRole="header" and focus it on mount.

  8. Testing. iOS: Xcode → Open Developer Tool → Accessibility Inspector, target the Simulator, walk the element hierarchy and run the audit; then verify real speech order on a physical iPhone. Android: TalkBack on the emulator requires a Google Play system image (AOSP images generally lack Android Accessibility Suite) — enable via Settings → Accessibility → TalkBack per Android's testing guide, then check linear swipe order, that every element is reachable, and that alerts are read aloud. Budget for the fact that Accessibility Inspector does not speak, so announcement ordering and interruption bugs will only surface on a real device.

WHAT TO CALL OUT IN THE CASE STUDY: the entire accessibility layer is core react-native with zero native modules and zero config plugins (fact 13), so it costs nothing against the Expo Go / npx expo start constraint — unlike the camera/library picker, which is where your custom-dev-build risk actually sits.

Recommendation

Use (a): a hand-rolled, typed in-app fake API module. It is the only option that survives the hard constraint "clean clone + npx expo start, Expo Go, no dev build" without qualification.

Shape it like a real client so the reviewer sees the seam, not a pile of setTimeouts. One transport shim, three services:

  • src/services/http.ts — async function request<T>(endpoint: Endpoint, produce: () => T, init?: {signal?: AbortSignal}): Promise<T> that (1) awaits a jittered delay from config, (2) consults a fault map, (3) throws typed errors (NetworkError | ServerError | TimeoutError | ValidationError) so the UI can distinguish offline from 500 from 422.
  • src/services/recipients.ts (getRecipients()), src/services/questions.ts (getQuestions(practiceId)), src/services/econsult.ts (createEconsult(draft) then uploadAttachment(econsultId, asset)).
  • src/fixtures/*.json imported statically (Metro inlines JSON at bundle time, no I/O, works identically in Expo Go on both platforms).

Deterministic failure: make uploadAttachment the forced-failure endpoint. It is the second of the two sending calls, so failing it deterministically demonstrates the genuinely interesting state — e-consult created, attachment not uploaded — which is a partial success needing a retry-attachment path, not a blanket "sending failed". Drive it from a faults: Record<Endpoint, 'none' | 'network' | 'server' | 'timeout'> record.

Config layering: defaults from EXPO_PUBLIC_* read as literal dot-notation (process.env.EXPO_PUBLIC_PRACTICE_ID, process.env.EXPO_PUBLIC_API_LATENCY_MS, process.env.EXPO_PUBLIC_FAIL_UPLOAD), committed as a .env plus .env.example so a clean clone behaves the same for the reviewer. Because those values are inlined at bundle time and need a full app reload to change, they are seeds only — never the live toggle.

Runtime overrides live in a React context (DevSettingsProvider holding {practiceId, latencyMs, faults, forceOffline} in useState), and the fake API reads config through that context (or a useSyncExternalStore-backed store), not from module-level mutable globals — React Compiler is enabled in this project, so mutating module state during render is exactly the pattern it will punish. Gate the panel with if (__DEV__) at the render site and behind a hidden expo-router route (e.g. app/(dev)/settings.tsx plus a triple-tap on the header title, which keeps the production a11y tree clean for VoiceOver/TalkBack users). Reject (b) msw: two open, unanswered React Native issues (#2592 since Sep 2025, #2748 since May 2026), and the current 2.15.0 line has a live regression where mocked bodies come back empty in RN because the interceptor expects a .body ReadableStream that RN's whatwg-fetch Response does not have. That directly contradicts "runs from a clean clone with npx expo start" and hands the reviewer a networking puzzle instead of your UI.

Call this out explicitly in the README (2-3 sentences: fake API chosen deliberately, real-client-shaped seam, how to flip failures) — showing you evaluated msw and a local server and rejected them for reviewer-reproducibility reasons is itself a point in your favour.

Topic: data-fetching

Data fetching + form state for a 4-step e-consult flow on Expo SDK 57 / React 19.2 with React Compiler enabled (TanStack Query v5 vs plain hooks, draft state across expo-router screens, zod validation)

Recommendation

Ship three dependencies: @tanstack/react-query@5.102.8, expo-network@~57.0.2, zod@4.6.2. All are pure JS or bundled into Expo Go, so npx expo start from a clean clone still works — no development build cost.

Why Query rather than plain hooks here: the brief demands loading, empty, error, sending and offline states on poor connections, and Query gives four of them as data rather than code — isPending / isError / isSuccess for the screen, fetchStatus === 'paused' for offline, and isPending on the mutation for "sending". Its defaults already match the audience: queries retry 3x with exponential backoff capped at 30s, and in the default networkMode 'online' a request made while offline is paused and continued on reconnect instead of failing. Hand-rolled useEffect fetching would need a per-screen state machine plus cancellation and dedupe, and would still leave you writing your own offline handling. For a take-home judged on code quality, the RN-specific wiring is the part that reads as competence, so do it explicitly in a src/lib/queryClient.ts + root _layout.tsx: the documented expo-network onlineManager listener (with the getNetworkStateAsync seed) and the AppState focusManager effect guarded by Platform.OS !== 'web'. Derive the offline banner from the same expo-network state via useNetworkState() so the UI and Query agree.

Step 2's two requests: one useQueries call for recipients + practice questions with combine to expose a single { isPending, isError, isEmpty, data } — it is exactly the documented use and avoids two ad-hoc spinners. Step 4's send: one useMutation whose mutationFn awaits createEConsult(...) then uploadAttachment(id, photo) — a single isPending drives the sending screen and a single onSuccess navigates to confirmation. Two things to handle deliberately and mention in the README: mutations do not retry by default, so set retry explicitly (e.g. 1–2 with backoff) only on the idempotent-safe parts, and treat "consult created but upload failed" as its own outcome ("message sent, photo could not be attached — retry upload") rather than blindly retrying the pair, since a retry of the whole mutationFn would create a second e-consult.

Form/draft state: plain useReducer + a Context provider mounted on the expo-router group layout for the flow (e.g. src/app/(econsult)/_layout.tsx), with a discriminated-union action type. Zero dependencies, the draft naturally lives and dies with the flow (no manual reset like a module-level zustand store would need), it is trivially testable, and a pure reducer is exactly what the React Compiler wants. Skip react-hook-form: its strengths (uncontrolled perf, big schemas) do not apply to three-to-five practice-configured fields, and it still has documented React Compiler friction — the compiler forbids reading or writing ref.current during render, which is where RHF's register/reset path breaks, and the recommended fixes are useWatch/useFormState/Controller or the explicitly-temporary 'use no memo' directive. Adding a library you then have to opt out of the compiler for is a worse story than 40 lines of reducer. Skip zustand too, but name it in the README as the upgrade path if the draft ever needs to outlive the flow (persistence/resume).

React Compiler rules to respect while writing this: no mutation of props/state/refs during render (lazy if (ref.current === null) init is the one allowed case), keep the reducer pure, no conditional hooks. Expo compiles app code only — not node_modules — so Query's internals are untouched; your components are the surface that must be rules-clean. Run npx expo-doctor / the react-hook lint rules as evidence in the README.

zod: validate the two GET responses inside the queryFn with safeParse and map a parse failure onto the same error UI (a malformed practice-question payload should not crash a 78-year-old's screen), and infer the TS types from the schemas so there is one source of truth. 2kb gzipped, zero dependencies, TS 5.5+ — your tsconfig already has strict: true. Keep zod at the network boundary only; do not reach for it as a form-validation engine here, the reducer can hold the two or three "required" checks.

Expo Go-compatible photo downscaling for the e-consult attachment: expo-image-manipulator (SDK 57) pipeline to produce a ≤1 MB, ~1600px JPEG from an expo-image-picker asset

Recommendation

Add expo-image-manipulator (npx expo install expo-image-manipulator → ~57.0.17) — it is Included in Expo Go on SDK 57, so it costs nothing against the "clean clone + npx expo start" constraint, and it is the only way to bound pixel dimensions. Picker quality alone leaves a 4000x3000 capture at 4000x3000.

Pipeline (imperative, because this runs once on confirm rather than on render):

  1. Pick with quality: 1 (or omit and accept the default) and exif: false. Rationale: the manipulator re-encodes anyway, so picker compression is a wasted lossy generation, and the SDK 57 docs explicitly warn the picker's quality pass "may be bigger than the size of the original image" for already-compressed input and is ignored on iOS for .png/.bmp from the library. Do NOT stack quality: 0.6 with compress: 0.7 — that is double compression for no size benefit.
  2. Compute the resize argument from the asset's own width/height so you bound the long edge, not always the width: if width >= height pass { width: Math.min(1600, asset.width) }, else { height: Math.min(1600, asset.height) }. Passing one dimension preserves aspect ratio (documented). Guard on asset.width === 0 (documented as possible) by falling back to { width: 1600 }. Skip the manipulation entirely when the image is already under both the pixel and byte budget.
  3. const ctx = ImageManipulator.manipulate(asset.uri); ctx.resize(size); const img = await ctx.renderAsync(); const out = await img.saveAsync({ compress: 0.7, format: SaveFormat.JPEG }); — then img.release(); ctx.release(); in a finally. Releasing is not strictly required (GC handles it) but SharedObject's own JSDoc names "image bitmap" as the case where manual release is warranted, and the library's deprecated manipulateAsync does exactly this pair of release calls. Never set base64: true — that would materialize the image as a JS string on top of the Uint8Array the upload already builds.
  4. Measure the result with new File(out.uri).size from expo-file-system (already installed, Expo Go-compatible; ImageResult has no size field). Use this to (a) show the patient "Foto: 0,4 MB" before sending, and (b) optionally re-save once at compress: 0.5 if the first pass exceeds the budget. One retry, not a loop — a bisect costs multiple full decodes.
  5. Upload out.uri (a cache-directory file). Because expo/fetch normalizes any FormData body into a single Uint8Array in JS memory, the ~300–600 KB this pipeline produces is the difference between a survivable and a hostile upload on a poor connection; it also cuts retry cost, which matters more than first-attempt latency for the offline/flaky states in the brief.

Use useImageManipulator only if you want a live preview transform tied to a source in render — it auto-releases via useReleasingSharedObject. For a one-shot on-submit resize, the imperative manipulate() + explicit release is the cleaner fit.

For the case study writeup, the honest framing is: this is one extra Expo Go-compatible dependency that turns an unbounded multi-megabyte upload into a predictable sub-megabyte one, and it is the single highest-leverage change for the "poor connections" user.

Recommendation

Keep the Context on the flow's group layout as the single source of truth, but back it with a write-through AsyncStorage draft and treat the send as resumable rather than abortable.

  1. Draft persistence (small, boring, ~40 lines). One key, econsult.draft.v1, holding { schemaVersion, recipientId, answers, message, photo: { uri, mimeType, width, height } | null, econsultId: string | null, idempotencyKey, updatedAt }. Write it from the reducer with a ~500ms debounce (AsyncStorage is string-only, so JSON.stringify) AND flush immediately on AppState.addEventListener('change', ...) when the next state is inactive or background — iOS documents ~5 seconds before it "is terminated and purged from memory", and Android documents that onDestroy() is not guaranteed, so debounce-only would lose the last keystrokes. Hydrate in the group layout: render a hydrating state (you already have loading), then either resume on the step the user left or start clean. Clear the key on confirmation and on explicit discard.

  2. Photo. Do not trust the picker's cache URI across a relaunch — Expo defines Paths.cache as deletable by the system and Android says outright to "check for the existence of your cache files before reading them". Right after the picker resolves, await new File(asset.uri).copy(new File(Paths.document, 'econsult', name)) (expo-file-system is already a dep of expo, nothing to install), store the document-dir URI in the draft, and on restore check file.exists before showing the preview — if it's gone, restore the text and show "the photo could not be recovered, add it again" rather than a broken thumbnail. Android's getPendingResultAsync() still belongs in the same restore path.

  3. In-flight send. Do NOT abort on background/inactive — backgrounding to read an SMS code is the exact case you're protecting, and cancelling guarantees the failure you're trying to avoid. Reserve AbortController (which expo/fetch genuinely supports) for the user's own Cancel button and a hard timeout. Make call 1 idempotent: generate the Idempotency-Key once, persist it in the draft before the request, and send it on every retry, so replaying after a process death cannot create a duplicate e-consult. Persist econsultId the moment call 1 resolves. On the way back to active, reconcile: draft with an idempotencyKey but no econsultId -> re-issue call 1 (safe, idempotent); draft with econsultId but no attachment ack -> jump straight to call 2. Show an honest "we're checking whether your message was sent" state rather than a spinner that lies.

  4. Use the right transport per call. Call 1 (JSON create) via expo/fetch, which is a plain URLSessionConfiguration.default session on iOS — no documented continuation while suspended, so it must be resumable, not trusted. Call 2 (attachment) via expo-file-system's file.upload(url, { uploadType: UploadType.MULTIPART }), whose iOS sessionType already defaults to 'background' (a real URLSessionConfiguration.background) — Apple documents those transfers as continuing while the app is suspended, so the big, slow, flaky-connection part of the send is the part that survives backgrounding for free. Call this out in the write-up as a deliberate asymmetry, not an accident.

  5. Cost and honesty for the case study. Zero custom-dev-build cost: AsyncStorage 2.2.0 is Included in Expo Go, expo-file-system is already installed via expo. What you cannot claim is true background completion of the JSON call or a promise that survives process death — the recoverable-state design (idempotency key + persisted econsultId + resume on active) is what makes that acceptable, and saying so explicitly is stronger than pretending the send is atomic.

Dutch app language + screen-reader pronunciation (VoiceOver/TalkBack) in Expo SDK 57 / RN 0.86.3, and what works in Expo Go vs only in a prebuild/EAS binary

Recommendation

Do the JS-only fix and explicitly scope the rest as out-of-scope-for-Expo-Go in your README.

  1. iOS, works in Expo Go today, zero dependencies: set accessibilityLanguage="nl-NL" on every element that carries Dutch accessibilityLabel/accessibilityHint/accessibilityValue. It is a core RN view prop registered in BaseViewConfig.ios.js (no native module), so Expo Go's prebuilt binary already supports it. Because RCTViewComponentView.mm applies it only to the view's own accessibility element and nothing propagates from ancestors, wrapping the app root in one <View accessibilityLanguage="nl-NL"> does NOT work — put it on each accessible node. Practical way to not scatter it: build thin wrappers (<AppText>, <AppButton>, <AppTouchable>) that default accessibilityLanguage={Platform.OS === 'ios' ? 'nl-NL' : undefined}, and set it once per screen-level accessible element — recipient rows, question options, the send button, error/offline banners, the confirmation summary. Same for AccessibilityInfo.announceForAccessibility targets (the announcement string itself has no language param, so the wrapper trick is the only lever).

  2. Android/TalkBack: state plainly in the README that there is no per-view language API — LocaleSpan is absent from react-native 0.86.3 and RN#35813 was closed without an Android equivalent. TalkBack reads Dutch using whatever TTS locale the device is set to, so the only mitigation is setting the emulator's system language to Nederlands when demoing, which you should note as a manual test step rather than code.

  3. Do NOT add expo-localization for this. It only reads the locale; it cannot set the app language, and its supportedLocales per-app-language feature is a config plugin evaluated only during npx expo prebuild. Same for locales + ios.infoPlist.CFBundleAllowMixedLocalizations — those write InfoPlist.strings at prebuild and are invisible in Expo Go, which is also why your Dutch camera/library permission copy will not appear in the reviewer's Expo Go prompts.

  4. Turn the gap into a credible README line instead of hiding it: "App is nl-NL only. iOS VoiceOver pronunciation is forced via accessibilityLanguage; Android has no equivalent API, so TalkBack follows the device TTS locale. Localized system permission dialogs and per-app language selection require locales + ios.infoPlist.CFBundleAllowMixedLocalizations and the expo-localization config plugin's supportedLocales, all of which only take effect in a prebuild/EAS build — deliberately skipped to keep npx expo start in Expo Go working from a clean clone." That sentence demonstrates exactly the Expo Go-cost awareness the brief asks for.

  5. Demo hygiene: because the iOS Simulator defaults to English, record/demo with VoiceOver on a Simulator left in English to prove the accessibilityLanguage fix actually changes the voice — that is the visible payoff.
