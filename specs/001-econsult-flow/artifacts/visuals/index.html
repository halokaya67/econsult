Flow record · 001-econsult-flow · Simulator previews

Simulator previews, step by step

Six of the twenty-two steps added a screen. Each of those was driven on an iPhone 17 simulator before it was allowed to pass, at the default text size and at the largest accessibility size. Where a run found a defect, the fix was made and the screen re-driven until it passed.

← Back to the record

Every page below is the evidence page the run itself produced: annotated screenshots with the measurements they were read from. The runs are listed in the order they happened, and the last one in each list is the page the progress board links to. The board reaches them as T015.html to T020.html, which are copies of those final pages.

T015

App shell: providers, root stack, home screen, the flow group with placeholder screens, and the test flow layout

Final page: home at the default and largest text sizes, plus the first-step placeholder.

  • T015-phone final

    Home renders cleanly at both text sizes. One defect reported: the placeholder first step shows a header with a title and no back control, so the invisible edge-swipe gesture is the only way out. The lead carried it forward to T016, which builds the header Home button.

T016

Step 1, the recipient screen

Final page: the header re-check at the largest text size after the font-scale cap.

  • T016-phone

    Seven captures of the loaded, loading, error, empty and preselected list. Two defects flagged: the header Home label is clipped to about half its glyph height at the largest text size, and the Continue hint is announced even when Continue is enabled.

  • T016-phone-recheck final

    Re-check after capping that one button's font scaling at 1.3, the way iOS caps its own bar buttons: the label now reads in full, with no defects. This also closes the flag T015 carried forward, because the Home control is the step's visible way out.

T017

Step 2, the questions screen

Final page: scroll-to-field lands the label 16 pt from the top with its error directly beneath, at both text sizes.

  • T017-phone

    Reported, not fixed. At the largest text size an invalid submit leaves the error above the top of the viewport with no scroll, so the tap looks like it did nothing; and the error text is not attached to any accessibility element, so a screen reader never reaches it.

  • T017-phone-recheck fail

    The error now folds into the question label's accessible name, but the scroll still never fires — and it throws. Measuring a view under the New Architecture needs a host instance, not the numeric node handle the first fix passed in.

  • T017-phone-recheck2 fail

    The scroll now lands to the pixel and the warning is gone, but the error is still rendered after the radio options, which alone fill more than the viewport — so at the largest size the label it scrolled to and the error it scrolled for are never on screen together.

  • T017-phone-recheck3 pass final

    With the error moved directly under the question label, the label lands 16 pt below the viewport top and the red error text is fully inside the viewport. The default text size is unchanged and clean.

T018

Step 3, the message screen with photo and sending

Final page: the re-check at the largest and default text sizes after the scroll-anchor fix. The first run's gallery covers pristine, keyboard, photo, sending and create failure.

  • T018-phone fail

    Seven of eight declared states render correctly. The eighth does not: an empty Send at the largest text size scrolls the input to the top, which pushes the field's own label 592 pt above the viewport and leaves the user looking at an unlabelled red box. The offline state could not be reached here and was deferred to T020, which builds the toggle for it.

  • T018-phone-recheck pass final

    All three re-checks pass. The label now lands 16 pt below the viewport top after an invalid submit, the default size no longer scroll-jumps at all, and the multiline box grows with the font scale to 471 pt.

T019

The confirmation screen

Final page: a failed photo retry reporting itself inside the alert at both text sizes. The first run's gallery covers sent, photo attached, partial failure, back blocked and Done.

  • T019-phone fail

    Eight of nine declared states render correctly. The ninth does not: after a failed “Try again” the alert is unchanged and nothing is announced, because a failed upload is an outcome rather than an exception, so the error path the screen renders never runs.

  • T019-phone-recheck pass final

    The retry that resolves as failed is now its own visible outcome: the alert gains a plain-language line, a second tap does not duplicate it, and both controls remain. Verified at the default and largest text sizes.

T020

Developer settings screen

Final page: the switch row wrapping and centring at the largest size, and Cancel leaving the modal without applying. The first run's gallery covers the practice switch and the offline message step.

  • T020-phone fail

    Five of six scenarios pass, including the offline state deferred from T018 — the banner shows, Send is disabled and reads are still served from the cache. The sixth fails: at the largest text size the “Force offline” label neither shrinks nor wraps, so it pushes the native switch past the right edge of the screen. Two smaller notes: the switch paints high of its label, and the modal has no exit but Apply.

  • T020-phone-recheck pass final

    All three checks pass. The label wraps, the switch sits fully inside the screen with its rounded cap intact and is centred on the row to within half a point at both text sizes, and the new Cancel button leaves the modal without applying the draft.

Steps without a preview

The other sixteen steps built contracts, transport, services, state, hooks, validation, the send pipeline, photo processing and the shared components. None of them put a new screen on the device, so the plan declared no visual for them and they were verified by their tests, types and lint alone.
