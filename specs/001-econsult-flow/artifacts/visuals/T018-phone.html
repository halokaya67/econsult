The input itself lands 18 pt below the viewport top, so the scroll ran correctly and hit its spacing.md margin, and the red error is fully painted from 268 to 611. The label ends at −476, 592 pt above the fold. The hint’s box ends at 128, but those last 12 pt are line-height leading: no hint glyphs are painted either, which the screenshot confirms — its first content row is the input’s red border.

The same thing happens at the default text size, 37.3 pt short instead of 592, which is why scenario 3 still passes all three of its declared checks while showing no label.

Defect flags
BLOCKING

Invalid submit hides the field’s label at the largest text size

src/app/econsult/message.tsx · src/components/TextField.tsx · src/components/ScreenScaffold.tsx

The screen hands scrollFieldIntoView the ref it put on TextField, and TextField forwards that ref straight to its inner TextInput. The scroll therefore measures the input rather than the field group, so the label and hint that sit above the input inside the same wrapper are pushed off the top — 592 pt of them at AX3XL. The questions screen passes the label node, which is why T017 passed the equivalent check.

Screen-reader users are unaffected: the input’s accessible name still reads “What would you like to ask?. Error: Please write your question before sending”. This is a sighted-large-text failure.

MINOR

The same scroll target misses by 37 pt at the default text size

label bottom 78.67 vs viewport top 116 · a11y-empty-send-default.txt

Same root cause, much smaller magnitude: the label and all but the leading of the hint are off screen at medium too. The error itself is unmissable and the screen is short, so scenario 3’s declared checks still pass.

MINOR

The multiline input does not grow with Dynamic Type

MULTILINE_MIN_HEIGHT = 132 · src/components/TextField.tsx

At AX3XL the box still measures 128 pt while its text renders at roughly 3× body size, so about a line and a half is visible while typing. Outside this step’s declared scenarios; noted for the accessibility pass.

Worth knowing
  • The scenario’s “two source actions” cannot exist on a simulator. PhotoPicker gates the camera action on Device.isDevice, false in Expo Go on a simulator, so the block renders one action plus the note “The camera isn’t available on this device.” That is the component behaving as written, but the two-action layout stays unverified until a physical-device pass.
  • “Preparing photo” was not captured in two attempts — a screenshot fired in the same command as the picker tap, then a six-shot burst. Photo processing finishes on a local simulator asset faster than a screenshot round-trip, while the picker sheet is still animating away.
  • VoiceOver announcement and focus order remain unverified. The screen calls announce() and focusForScreenReader() on an invalid submit, but neither announcements nor screen-reader focus could be captured on this device.
